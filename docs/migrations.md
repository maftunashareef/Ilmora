# Миграции базы — как писать

Схему и миграции меняет один чат (база данных, Тимур). Правила проверяет `apps/api/test/migrations.test.ts` — CI не
пропустит миграцию, которая их нарушает. Почему так — проверка 11.11, №87 и №122.

## Правила

1. **Применённые на боевой миграции не трогать.** Prisma хранит их контрольную сумму; исправленная задним числом
   миграция больше не совпадает с тем, что выполнила база. Нужно что-то поменять — новая миграция. Суммы 26 миграций до
   релиза 54 закреплены в тесте; когда новая миграция дойдёт до боевой, её сумму добавляют туда же.
2. **Одна транзакция.** Файл начинается с `BEGIN;` и заканчивается `COMMIT;`. Без этого миграция, упавшая на середине,
   оставляет схему наполовину изменённой, и каждый следующий релиз встаёт на P3009. В транзакции ошибка откатывает всё:
   база такая же, как до релиза (проверено на копии).
3. **`SET LOCAL lock_timeout = '3s';` сразу после `BEGIN;`** (не больше 5 с). `ALTER TABLE` ждёт, пока таблицу
   отпустят, — например, ночная копия (`pg_dump`, 03:40 по Ташкенту) или долгий запрос, — а все запросы к этой таблице
   ждут за ним: сайт висит (замерено 6,6 с). С ограничением миграция через 3 с падает и откатывается, запросы ждут не
   дольше 3 с (замерено 2,9 с); релиз повторяют (README серверов, «Миграция упала»).
4. **Совместимо с прошлым релизом.** Релиз сначала мигрирует базу, потом меняет код, а откат возвращает старый код на
   новую схему. Поэтому в одном релизе только добавляем: новые таблицы, колонки с умолчанием или `NULL`. Удаление и
   переименование — через релиз, когда старый код уже не читает старое. Если миграция всё же ломает старый код (как
   проверка возвратов в `20261117000000`), граница отката поднимается — записать в README серверов, раздел «Откат».
5. **Чего нет в `schema.prisma`** — CHECK-ограничения, частичные индексы — пишут прямо в SQL миграции. `migrate diff`
   (проверка в CI) их не видит и не ругается.
6. **`CREATE INDEX CONCURRENTLY`** в транзакции не работает. Такой оператор — отдельной миграцией, первой строкой
   комментарий `-- no-transaction: <почему>`, затем `SET lock_timeout = '3s';` (без `LOCAL`), сам оператор, и больше
   ничего.

## Как сделать

```bash
cd apps/api
# SQL по разнице между миграциями и схемой (нужна пустая база для SHADOW_DATABASE_URL)
SHADOW_DATABASE_URL=postgresql://…/ilmora_shadow npx prisma migrate diff \
  --from-migrations prisma/migrations --to-schema prisma/schema.prisma --script > /tmp/new.sql
mkdir prisma/migrations/ГГГГММДДччммсс_коротко    # время — позже последней миграции
```

В `migration.sql`:

```sql
-- Что и зачем (задача, кто просил). Совместимо с кодом прошлого релиза: почему.
BEGIN;
SET LOCAL lock_timeout = '3s';

-- … SQL из /tmp/new.sql, затем заполнение данных и CHECK, если нужны …

COMMIT;
```

Проверить: `npm run test -w apps/api` (правила и всё остальное), `npx prisma migrate deploy` на копии базы с данными,
`migrate diff --exit-code` — без расхождений. Образец — `20261118000000_payment_one_pending_per_subscription`.
